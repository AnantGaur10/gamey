## 7. Research, answers and rejected ideas (same day; no code unless noted)
- **WebGPU / WASM: rejected.** WebGPU still needs a WebGL2 fallback on the Chromebook/Safari targets (QA: poor there = disabled on that platform) and would mean rewriting every custom shader (`addDirtDetail`, hell lava/sky/eclipse/runes, rim, post) in TSL; the scene is small (~40k tris before the backdrop). WASM: the logic (DuelMachine, bullets, 10-body cannon ragdoll) is microseconds of JS; only revisit Rapier if the ragdoll ever profiles hot.
- **Low-end perf reasoning.** Triangles were never the bottleneck; draw calls were (cowboys 73 meshes each = ~146 of ~157 calls). Rough comfortable WebGL limits used for planning: 4GB Chromebook / budget Android ~100-300k tris and ~100-150 draw calls at 60fps. Software GL (SwiftShader, also what blocklisted GPUs get) is fill-bound: full-screen passes cost far more than draw calls there, hence the post-pass watchdog (§1). Pasted generic advice reviewed: InstancedMesh (already used where it fits: hell columns/volcanoes; cowboys can't be instanced), texture atlas (vertex colours do it with zero texture bytes), shadows (no shadow map already), bake lighting + Lambert (the useful part: done for the cowboys in §1).
- **3-5k cowboy tri budget** is our own rule (`context/2026-09-24.md` §106, locked 09-29), not a CrazyGames rule; reasons: download size (20MB mobile homepage), weak devices, invisible bevels at 6-25m. The "~14k tris" CLAUDE.md drift note was stale (fixed 10-04: 4348/4392); removed today.
- **Zone shrinks with the ring (user idea, rejected after playing).** "If the circumference halves, the gold area should drop 75%" = zone share proportional to ring size (arc ~ size²). Simulated with the real classes: with an 8% floor good players end ~0.21° (vs 0.051° now), average ~0.66°, spam ~1.07°; lower floors were harsher. The plan was approved then withdrawn: "the idea i just gave now should be negated i think its too much when i played it". Zone stays: 22% start, x0.86 per hit, 8% floor, misses don't widen it.
- **How CrazyGames keeps progress (docs.crazygames.com /sdk/data, /requirements/account-integration, /other/aps, /sdk/intro, /sdk/user, /sdk/video-ads):**
  - Data module (`SDK.data.getItem/setItem/removeItem/clear`, localStorage-like, writes debounced ~1s up to 30s, 1MB JSON cap): guests -> local storage on that device; logged-in -> saved to the CrazyGames account and synced across devices; a guest who logs in has the local data uploaded only if the account has no cloud save; logout falls back to the guest data. CrazyGames says to rely on it fully and not also write localStorage yourself.
  - APS (Automatic Progress Save): backs up/restores the game's own `window.localStorage` (HTML5) or IndexedDB (Unity) to the logged-in account with no code; not allowed for games with in-game purchases (it trusts local data); 1MB cap. Not documented: whether it runs on a Basic launch without the SDK, conflict rules between devices, incognito.
  - Incognito (browser behaviour, not CrazyGames docs): storage lasts for the window only; guests lose progress on close, logged-in players get the cloud copy back. `SafeStore` keeps an in-memory copy so nothing crashes.
  - Checklist: a Full launch needs Data module or APS (or a written N/A); don't rely only on local data (shared devices).
  - Our shop spends earned gold, very likely not "in-game purchases" (real money), but the Data module (§6) is the safe choice either way.
